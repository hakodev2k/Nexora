## Findings

### IR-01 — Medium: denied source links influence pagination and continuation

**Location:** `src/Nexora.Infrastructure/Sharing/SqlSharingService.cs:109–120`, `:146`, `:160–174`.

`ReadListAdvisories` selects TOP(26) owner/epoch/filter-matching links before source authorization. `List` computes `hasMore` and takes25 before calling `OwnerSourceAllowed`. The continuation is then derived from the last advisory row, including a denied row, rather than the last authorized result.

**Concrete condition:** an Admin retains `sharing.link.read` but loses the applicable Project/Document read/share action or source module entitlement after creating links. With26 matching links to denied sources, the response has no items but a non-null continuation; with no matching links it has no continuation. A guessed `resourceId` filter can therefore expose the presence of enough currently unauthorized links. Mixed authorized/denied results also produce short or empty pages and a continuation based on hidden records. The cursor is encrypted/authenticated, which protects its contents but does not hide its presence or the number of pages.

**Contract:** D07's count/pagination rules require current source authorization before disclosure and exclude metadata/count leakage after source denial. Also NXG-SYS-02/03/08, FX04 current source rules and the D05 count/projection boundary. This is an existence/cardinality side channel within the same owner's restricted context, not evidence of a cross-owner body/token leak.

**Required repair:** calculate visible page membership and `hasMore` only from current-authorized rows in a consistent transaction, preserving source-before-link lock ordering. An implementation may scan candidates internally, but denied-only candidates must not determine a public continuation. Cursor anchor validation must follow the same authorized-set semantics.

**Verification still required:** real SQL/API comparison of zero versus26 denied-only links; mixed allowed/denied sources; module/action revocation; all state/resource filters; concurrent policy/source changes; authorized paging with no skips/duplicates. Not run by this reviewer.

### IR-02 — Medium: compatibility receipt reader does not reject ambiguous successful outcomes

**Location:** `src/Nexora.Infrastructure/Identity/SqlRequestReceiptStore.cs:229–254`; dual subject namespaces in `SubjectHashes`; consumers `src/Nexora.Infrastructure/Organization/SqlTagService.cs:489–520` and `src/Nexora.Infrastructure/Documents/SqlDocumentTagService.cs:468–497`.

The receipt store reads both operation-qualified and operation-independent authenticated subject hashes. For active rows it checks request digests, then selects the first Succeeded row. It does not compare successful result ID/envelope/code/status across those rows. Two live receipts with identical canonical request digest but distinct valid V2 Tag-create outcomes therefore yield whichever success is ordered first. Tag service validation checks only that selected receipt; it cannot establish that the original committed Tag identity is unambiguous.

**Concrete persisted-state case:** two compatibility namespace rows for the same user, operation and key, with equal canonical request digest, both Succeeded/201/TagCreated, but valid envelopes identifying different TagIds. Replay returns one DTO or opaque ACK instead of a reconciliation conflict. If both Tags were removed, it still acknowledges one arbitrarily selected historical ID. No new write is needed to traverse this branch.

**Contract:** D08 expressly requires unprovable legacy receipts/collisions/ambiguous original-create binding to fail closed. Current action/namespace checks and an opaque response do not resolve ambiguity in original identity.

**Reachability limitation:** the unsafe branch is established by source inspection. This review has not established that an ordinary current caller can create these conflicting rows, nor that such rows exist in the owner's database. This is a persisted compatibility-state integrity gap, not a demonstrated external exploit or plaintext disclosure.

**Required repair:** reject conflicting active outcomes before selecting a replay; define and enforce which duplicate compatibility rows are provably equivalent, without choosing an arbitrary success or recreating a Tag. Preserve actor/action/digest/namespace checks, TTL and atomic receipt/business writes.

**Verification still required:** real SQL cases for equivalent versus divergent compatibility envelopes, conflicting status/code/ID, current denied write authority, deleted Tag, and cross-namespace receipts. Not run by this reviewer.

### IR-03 — Medium:26-row query batches do not bound request work or retained source state

**Location:** `SqlSharingService.cs:123–160`.

The loop stops only after26 actual authorized rows or advisory exhaustion. There is **no27-batch cap** in the inspected diff. A caller with a large matching denied-source history causes a scan of that entire history. Every distinct source is retained in `sourceAuthority`, including denied sources; Serializable policy/source locks remain held until the request finishes. Individual command timeouts do not bound the total duration of arbitrarily many commands. The second connection also increases per-request pool demand.

**Impact:** predictable per-request work/memory/lock-duration bounds are absent; many historical links or concurrent calls can consume SQL connections and prolong policy/lifecycle blocking. This is an availability/resource-governance issue, not renewed disclosure of denied rows in the response. TOP(26) and fixed public page size25 are insufficient bounds for this algorithm.

**Required disposition:** establish a request-wide scan/time/resource budget or a reviewed query/coordination design that bounds the work. Budget exhaustion must not invent a hidden-row continuation or falsely report a complete empty result. A safe retry/unavailable result needs an explicit contract; returning a different result solely at a denied-row threshold also requires privacy review rather than assuming the original side channel is gone. No numeric product limit is approved by this review.

**Additional implementation detail:** a batch is appended in full before the count check, so25 existing results plus26 next-batch rows can materialize51 authorized rows before trimming. This is bounded transient over-read, not a51-row public response, but the claim that only26 rows are ever materialized is inaccurate.

### Lock-order and cursor risks — pending, not reproduced deadlock findings

1. **Source-before-link holds per batch, not for the whole transaction.** At `:138–155` definitive link locks are acquired and retained. After `:159–160`, `:129–133` can acquire entirely new source/container locks. Sorting sources within each batch does not impose a global order across batches. Review the full graph against multi-source lifecycle/cohort writers and policy invalidation, not only single-source revoke/resolve. Consider an arrangement that does not acquire fresh source locks after definitive link locks; a bounded retry may be needed if definitive validation changes the selected set. This review does not prescribe a replacement architecture.
2. **Separate advisory connection creates an application-level wait edge.** The main transaction waits synchronously for a locking READ COMMITTED query on the other connection while retaining source/policy/link locks. If an intervening writer holds an advisory-visible link/index lock and waits for a main-transaction lock, the application wait can prevent SQL from seeing the full cycle. Plan-dependent range/page locks or lock escalation also matter. This is a concurrency risk requiring a demonstrated schedule/query-plan review, not a claim that the current regression reproduces a deadlock. Do not substitute NOLOCK or READPAST: dirty/skipped candidates can invalidate existence/paging semantics.
3. **Cursor link proof remains advisory.** The helper verifies anchor link/filter/epoch before the Serializable transaction, while the transaction rechecks the source only. A concurrent revoke or filter change of that anchor can therefore race between those steps. If the intended contract requires a currently eligible anchor link as well as current source authority, add definitive same-TX link/filter/identity revalidation after source proof. Otherwise record the allowed race explicitly. No hidden source body/token leak was established from this race.
4. **Overall ordering is stable for fixed data, not a snapshot of concurrent inserts.** Keyset advancement uses immutable CreatedAt/Id from each internal batch; qualifying inserts ahead of the internal boundary can be absent from the current page. Such non-snapshot pagination can be acceptable, but no claim of a fully Serializable candidate population is justified when candidate enumeration uses an independent connection. Current definitive owner/source authorization still protects returned rows.
